# 寶可夢 PTCG 全圖鑑收藏 App

依全國圖鑑整理 Pokémon TCG 卡片收藏的個人化 Web App。手機優先、支援深色／淺色模式、可安裝成 PWA，資料保存在本機瀏覽器的 IndexedDB。

## 啟動方式

**最簡單：雙擊資料夾裡的「啟動圖鑑.bat」**，它會自動啟動本機伺服器並開啟瀏覽器。那個黑色命令列視窗要保持開著，關掉就等於關掉 App；下次要用再雙擊一次即可。

不想用 .bat 的話，也可以自己在這個資料夾執行：

```bash
python start_app.py
```

或用最原始的方式：

```bash
cd "D:\ptcg 圖鑑"
python -m http.server 8811
```

然後打開 `http://localhost:8811`。

> 一定要透過 HTTP(S) 伺服器開啟（上面任一種方式都可以），**不能直接雙擊 `index.html` 用 `file://` 開啟**，否則 `fetch()` 讀取 `data/*.json` 與 PWA 的 Service Worker 都無法運作。
>
> `start_app.py` 同時監聽 IPv4 與 IPv6（只綁 IPv4 的話，瀏覽器把 `localhost` 解析成 `::1` 時會連不上）。

### ⚠️ 一定要固定用同一個網址（連接埠）

瀏覽器的 IndexedDB 是**依網址（含連接埠）分開存放**的：`localhost:8811` 與 `localhost:8812` 對瀏覽器來說是兩個不同的網站，收藏紀錄與手動上傳的圖片**不會互通**。

舊版啟動器在 8811 被占用時會自動往 8812、8813… 找，結果是：忘了關上一個黑色視窗就再雙擊一次，這次就會跑到新的連接埠，先前存的收藏與自訂圖片看起來像「全部不見了」（其實還在舊網址底下）。

現在啟動器改成：8811 綁不上時，先讀 `http://127.0.0.1:8811/data/app_id.txt` 確認占用的是不是同一個圖鑑；是的話就**直接沿用它、不另開伺服器**，網址永遠維持 `localhost:8811`。真的被其他程式占用時才會換埠，而且會在視窗裡明講「這個網址底下的資料會是空的」。

另外，「匯出 JSON 備份」現在會**一併包含手動上傳／採用的圖片**（`formatVersion: 2`，base64），換瀏覽器、換電腦或萬一真的跑到別的連接埠時，可以靠這份備份把圖片一起搬回來；舊版 `formatVersion: 1` 的備份檔仍可正常匯入，且不會清掉裝置上現有的圖片。

### 從 GitHub clone 下來之後（卡圖會自動補下載）

repo 裡**不包含 `images/` 資料夾**（約 957 MB、16,900 個檔案，而且是官方卡圖，不適合重新散布），也不包含第三方補圖包 `exports/` 與本機圖片對照表 `data/image_local_map.json`。

**不需要手動做任何事**：執行 `start_app.py`（或雙擊「啟動圖鑑.bat」）時會自動檢查本機缺哪些圖，缺的話就在**背景一邊下載一邊讓你用 App**，不會卡住不讓你開。下載流程可續傳，關視窗中斷沒關係，下次啟動會接著補。

clone 下來、還沒補圖完成時的顯示狀況：

| | 補圖完成後 | 剛 clone、還在背景下載時 |
|---|---|---|
| 寶可夢立繪 1,025 張 | 本機檔案 | 自動用 PokéAPI 遠端網址，正常顯示 |
| 卡片圖 11,782 張 | 本機檔案 | 自動用 TCGdex 遠端網址，正常顯示 |
| 卡片圖 4,028 張 | 本機檔案 | 顯示「圖片無法載入」替代畫面（來源資料本身沒有圖片網址，圖是後來從 LimitlessTCG 補的） |
| 卡片圖 36 張 | 本機檔案 | **無法自動取得**，需要自備 `exports/missing_images` 補圖包，或用 App 內的手動上傳功能 |

圖片載入的優先順序是**本機檔案 → 原始遠端網址 → 佔位圖**，所以背景補圖跑到一半也不會整頁破圖。

想自己控制的話：

```bash
python setup_images.py
```

不想要自動下載：在 `data/` 底下建立一個空檔案 `.no_auto_download` 即可（App 照樣能用，缺圖的卡片顯示替代畫面）。

補圖需要 `requests` 與 `Pillow`；沒裝的話啟動器會直接告訴你要跑哪一行 `pip install`，不會丟一堆 traceback。

> 收藏紀錄存在瀏覽器的 IndexedDB，不在 repo 裡，clone 不會帶走也不會覆蓋任何人的收藏。

安裝成 PWA：用手機瀏覽器打開網址後，選「加入主畫面」。正式部署時建議放在有 HTTPS 的網域，PWA 安裝與 Service Worker 才會完整生效（localhost 開發時例外，瀏覽器允許）。

## 資料來源與收錄範圍

### 全國圖鑑資料（`data/species.json`）
- 來源：[PokéAPI](https://pokeapi.co)（公開開放資料，免金鑰，GraphQL 介面）。
- 內容：全國圖鑑編號、繁體中文名稱（`zh-Hant`）、英文名稱、世代、傳說／幻獸標記、進化來源編號、官方立繪圖網址。
- 範圍：第 1–9 世代，共 **1025** 筆物種資料。不含地區形態、超級進化、性別差異圖等變體——這些設計上會掛在對應本體寶可夢下管理，不會另外佔用圖鑑編號（目前卡片資料裡也還沒有實際的變體卡片可以展示這個機制）。

- **缺稀有度資料**：2,354 張（日文 2,315 張、約 31%；英文 39 張）。這些卡片會被歸在「其他」分類，並在詳細頁明確標示「稀有度資料尚未提供」，不會被誤標成某個確定的稀有度。

**這仍然不是官方歷年全卡表**：只匯入了 Sword & Shield 世代之後（AR/SAR/CHR/CSR/UR 這套現代稀有度制度適用的年代）的日文與英文卡片，不含更早期的系列（例如 XY、SM、更早的中文版）。要擴大範圍請見 `data/pipeline/README.md`。

本站沒有取得 kajiku.tw 或 pokecardex.com 的公開 API，這兩個網站也沒有公開 API 可用；App 內建的分類徽章樣式（AR／CHR／CSR／SAR／SR／UR／PROMO）參考了這兩個網站常見的收藏分類概念做版面設計，但卡片資料庫是獨立從 TCGdex 建立的，不是從這兩站抓取。

### 圖片：本機快取（`images/` + `data/image_local_map.json`）

寶可夢立繪與卡片圖片原本是直接 hotlink 遠端網址（PokéAPI 的 GitHub sprites／TCGdex 的 `assets.tcgdex.net`）。現在改成實際下載到本機 `images/species/` 與 `images/cards/`，App 載入時會優先使用本機檔案，本機沒有才退回遠端網址（遠端也失效的話，畫面會顯示清楚的「圖片無法載入」替代畫面，不會空白或報錯）。

下載流程（`data/pipeline/step5_download_images.py`）：逾時 20 秒、失敗重試最多 4 次且間隔遞增、遇到 429 會讀 `Retry-After` 標頭等待；卡片圖片會依序嘗試 `low.webp -> low.png -> high.webp -> high.png` 四種畫質／格式組合（實測發現 TCGdex 常有「`low.webp` 404 但其他格式其實有圖」的情況）；下載完一律用 Pillow 開檔驗證是可解碼的圖片才存檔，不會把錯誤頁存成圖檔。整個流程可續傳，重跑只會處理還沒成功或本機檔案不見的項目。

**結果**：**15,846 / 15,846 張卡片（100%）與全部 1,025 張寶可夢立繪都有本機圖片**，來源如下：

| 來源 | 張數 | 說明 |
|---|---|---|
| TCGdex | 11,782 | 原始資料有提供圖片網址的卡片，100% 下載成功 |
| LimitlessTCG（英文庫） | 474 | `step9_fetch_limitless_fallback.py` |
| LimitlessTCG（日文庫） | 3,415 | `step11_fetch_limitless_jp_fallback.py` |
| tcgcollector 補圖包 | 139 | `step12_import_export_package.py`，匯入前重新獨立複驗 |
| tcgcollector 補圖包（版本未核對） | 36 | `step14_apply_candidates.py`，卡包與卡名核對過、印刷版本無法核對 |

LimitlessTCG 補的 3,889 張圖，每張都是先抓該卡的頁面、比對頁面顯示的卡名與卡包／卡號一致才採用，**不是用名稱去猜圖片網址**；使用者提供的另外三個來源（Pokéllector、pokemon-card.com 官網、Scrydex）評估後皆未用於自動下載，理由見 [`data/pipeline/README.md`](data/pipeline/README.md)。

最後那 36 張（My First Battle 34 張、SVP Jumbo 1 張、MEP 1 張）在兩個資料庫之間的編號規則不同：mfb 是 TCGdex 用整體清單編號、來源按四副牌各自編號。這種情況**核對得到卡包與卡名，核對不到印刷版本**。

> 原本這裡是 44 張。後來發現其中 8 張 MC 基本能量其實抓得到：LimitlessTCG 有收錄「Starter Decks 100 Battle Collection (MC)」，只是那 8 張基本能量在它那邊用單字母編號（`G`／`R`／`W`／`L`／`P`／`F`／`D`／`M`），而 TCGdex 用三字母屬性碼（`GRA`／`FIR`…），所以一開始比對不到。補上 `JP_NUMBER_OVERRIDES` 逐張對照、再核對卡名之後，這 8 張改由 LimitlessTCG 取得，版本也因此從「未核對」變成可驗證。

這 36 張依使用者指示已直接套用（`step14_apply_candidates.py`），並在 manifest 裡誠實標成 `source: tcgcollector_package_candidate`、`verifiedBy: setName+cardName（版本未能核對）`，不會混充成完全驗證過的資料。

挑選規則：同一張卡有多個候選時，取來源編號最小的那張（實測 My First Battle 四副牌的成對候選，編號小的是牌組限定的藍框／精靈球標記版，編號大的是一般版）；編號相同時（Potion／Switch 四副牌各一張，只差右下角牌組符號）取清單第一張。這 10 張有其他版本的卡片，平常不會佔版面：卡包資訊那行旁邊只有一顆小按鈕「換版本 N」，按下才展開其他版本的候選圖，按「改用這張」即可換，按卡片圖上的「×」就回到預設。

人工覆核用的清單（含縮圖、卡包、卡號、語言、來源連結）另外輸出成 Word：`PTCG圖鑑_待人工覆核卡片清單.docx`（`step15_build_word_report.py`），決策紀錄見 `data/pipeline/logs/candidate_decisions.json`。

`images/` 資料夾體積較大，沒有放進交付的壓縮包；`data/image_local_map.json`（本機路徑對照表）本身很小，有納入交付包，即使沒有 `images/` 資料夾 App 也能正常運作（全部退回遠端網址）。要重新產生本機圖片，跑 `python data/pipeline/step5_download_images.py` 再 `python data/pipeline/step6_build_image_map.py` 即可。

各分類相加是 15,848，實際不重複卡片是 **15,846** 張 —— 差的 2 張是同時帶有稀有度的宣傳卡，會同時列在「PR／PROMO」與它的稀有度分類裡。這只是同一筆資料出現在兩個清單，資料庫仍然只有一筆卡片與一筆收藏紀錄，統計一律以不重複的卡片 id 計算。

### 為什麼對照表要分語言

TCGdex 的 `rarity` 是它自己的一套英文正規化用語，**同一個字串在日文卡與英文卡上不一定代表同一個等級**。我直接打開本機卡圖、放大讀卡面右下角的印刷代碼核對，結果如下：

| TCGdex 字串 | 核對的卡片 | 卡面印的代碼 |
|---|---|---|
| `Ultra Rare` | 日版 S10P #068 スピアーV | **SR** |
| `Mega Hyper Rare` | 日版 S10P #086 オリジンパルキアVSTAR | **UR** |
| `Hyper rare` | 日版 S8 #116 シャンデラVMAX | **HR** |
| `Secret Rare` | 日版 S8 #125 モココ | **UR** |
| `Illustration rare` | 日版 S12a #173 | **AR** |
| `Special illustration rare` | 日版 S12a #210 | **SAR** |
| `Character Rare` | 日版 S11a #069 | **CHR** |
| `Character Super Rare` | 日版 S11a #084 | **CSR** |

也就是說，把英文的 `Ultra Rare` 直接當成日版 UR 是錯的 —— 它其實是日版的 **SR**；日版 UR 對應到的是 `Secret Rare` 與 `Mega Hyper Rare`。而且日文與英文的 `Secret Rare` / `Hyper rare` 指涉的等級剛好相反（英文 Secret Rare 抽驗到的是彩虹卡，日文 Secret Rare 印的是 UR 金卡）。這個錯誤原本就存在於舊版 `js/categories.js`，已一併修正，並用 `BUILTIN_RARITY_MAPPING_VERSION` 讓既有裝置上的內建分類自動重新同步（使用者自建的分類不受影響，收藏紀錄也不會變動）。

規則帶有 `confidence` 欄位：`printed`（已核對卡面代碼）、`structural`（卡圖解析度不足，改用卡包編號位置推定）、`tier`（英文卡不印日版代碼，依英文版等級名稱對應）、`unresolved`（無法確認）。不是 `printed` 的規則會在卡片上顯示標記。

### 待確認（2,640 張）

刻意不猜、也不併進普通卡的卡片，原因有三種：

| 原因 | 張數 |
|---|---:|
| 日文卡：來源資料沒有提供稀有度（TCGdex 日文資料完整度約 71%） | 2,315 |
| 英文卡：`Secret Rare` 同時涵蓋彩虹卡與金卡，光看字串無法判斷該歸 HR 還是 UR | 286 |
| 英文卡：來源資料沒有提供稀有度 | 39 |

### 功能

搜尋（寶可夢中／英文名、卡片名、卡號、卡包名）、篩選（全部／已收藏／未收藏、語言、卡包）、排序（圖鑑編號或卡包＋卡號）、點卡圖開該寶可夢的詳細頁、就地增減持有張數。分類頁與圖鑑頁、我的收藏共用同一份 `cardOwnership`，任一邊改動另一邊即時同步。「手動點亮某隻寶可夢的某個分類」屬於 `manualFlags`，不會被當成實際卡片收藏，也不會計入分類頁的「已收藏」數。

## 手動確認分類與匯出卡表

### 手動指定分類

每張卡片下方都有一個分類下拉選單（「卡片分類」頁的卡片格、以及寶可夢詳細頁的卡片列）。選好就立刻存檔，不需要另外按儲存；旁邊會顯示「已儲存」，失敗會跳出可重試的提示。存檔後那張卡會立刻從原分類消失、出現在新分類，各頁面的數字同步更新，並提供一次「復原」。

三層資料分開保存，彼此不覆蓋：

| 層 | 存在哪 | 會不會被改 |
|---|---|---|
| 來源原始稀有度 | `data/cards.json` 的 `originalRarity` | **永遠不動** |
| 系統自動判定 | 由 `js/cardCategories.js` 即時算出（`card.autoCategoryIds`） | 不存 DB，永遠可回溯 |
| 使用者手動指定 | IndexedDB `cardCategoryOverrides`，key 是穩定卡片 ID | 只有你改才會變 |

顯示與匯出時優先用手動，沒有手動才用自動。

- **「手動選待確認」與「恢復自動分類」是兩件事**：前者會寫入一筆 `categoryId: "UNVERIFIED"` 的紀錄（代表「我看過了，確實無法判斷」），後者是把整筆紀錄刪掉、回到系統判定。選單旁的「恢復自動」按鈕只在有手動指定時出現。
- **PROMO 並存不會被弄掉**：把一張宣傳卡的稀有度分類改成 AR，它仍然同時留在 PR／PROMO。只有主動把它指定成 PR／PROMO 時才會只屬於 PROMO。
- **分類修改不影響收藏**：持有張數與備註完全不動。
- 卡表換版時 `migrateCardIds()` 會一併把手動分類搬到新的卡片 ID。
- 手動分類**只存在這台瀏覽器**（IndexedDB），換瀏覽器或清除資料會消失，請用 JSON 備份搬移。

### 匯出卡表（`#/export`）

入口：「卡片分類」頁最上方的「📤 匯出卡表」按鈕，或「設定」頁的「匯出卡表（查看用）」。

可選：分類（可複選＋全選／全部取消）、卡片範圍（全部已收錄／只要已收藏／只要未收藏）、是否沿用「卡片分類」頁的搜尋與篩選。按鈕上方會即時顯示實際條件與預計卡片數。匯出前會再從 IndexedDB 同步一次手動分類，確保用的是最新結果。

**Excel（.xlsx）** — 用 SheetJS 產生真正的 OOXML（ZIP 簽章 `50 4B 03 04`）。三種工作表：

1. **全部明細** — 本次範圍內每個穩定卡片 ID 一列。一張卡屬於多個分類時，「目前所在分類」欄會列出全部（例如 `SR、PR／PROMO`），**不重複建列**。
2. **各分類明細** — 依所選分類各一張，內容同樣是逐卡完整資料，名稱套 Excel 限制（`PR／PROMO` → `PR_PROMO`，最長 31 字，去掉 `: \ / ? * [ ]`）。
3. **統計總覽** — 匯出時間、篩選條件、各分類卡片數／收藏數／持有總張數。輔助用，不取代明細。

每一列都是**逐張卡片的完整明細**，共 22 欄：穩定卡片 ID、全國圖鑑編號、寶可夢名稱、卡片名稱、目前所在分類、來源原始稀有度、分類依據（手動指定／系統判定）、語言／發行地區、所屬大系列、卡包／擴充包名稱、卡包代碼、系列代碼、完整卡號、版本／特殊標記、卡片標籤（ex／V／VMAX／VSTAR）、繪師、發售日期、已收藏／未收藏、持有張數、備註、卡片資料來源網址、圖片網址

同版本收了幾張用「持有張數」表示，不重複建列；不同卡包／卡號／語言的同名卡各自獨立一列。

**刻意沒有的欄位**：實體卡冊名稱／頁碼／格位。App 沒有保存這類實體收納位置資料，所以不輸出、也不自行填造，並在統計總覽裡寫明。「版本／特殊標記」只填資料已確認的內容（宣傳卡卡包、樣本資料）；異圖、閃卡、反閃、蓋章版來源資料庫並未提供，因此留空而不是猜測。
- 卡號強制存成文字，前導零與斜線都保留（`037`、`046/225`、`SWSH230/307`）
- 凍結標題列、自動篩選、欄寬都有；預設依圖鑑編號 → 卡包 → 卡號排序
- 總覽含匯出時間、匯出條件、各分類的不重複卡片數／已收藏數／持有總張數、本次不重複卡片總數，並註明重疊卡片不重複計算、本表不是官方完整卡表

**Word（.docx）** — 用 JSZip 自組 WordprocessingML，也是真正的 OOXML。依分類分章節，每章一個表格（卡片名稱、卡包、卡號、語言、收藏狀態、張數），A4 直式、表格欄寬總和壓在版面寬度內、標題列跨頁重複。

兩個函式庫都放在專案內的 `vendor/`（`xlsx.full.min.js`、`jszip.min.js`），不靠 CDN，離線可用，需要時才載入。

> Excel／Word 是**查看用**，不能還原資料。要備份請用「設定」頁的 JSON 備份 —— 它現在一併包含手動分類（`categoryOverrides`，以穩定卡片 ID 保存）、收藏紀錄與自訂圖片。

## 批量移動分類與清除收藏

### 新增的手動專用分類

除了原本 11 個分類，另外加入 **RR、RRR、光輝、ACE、SSR、BWR、MUR、MA、閃光**。

這 9 個在 `js/cardCategories.js` 裡標了 `manualOnly: true`，而且**刻意沒有任何自動對照規則** —— `RARITY_RULES` 裡完全找不到它們，所以 `classifyCard()` 永遠不會把卡片放進去，即使某張卡的原始稀有度字面上看起來很像。要有卡片只能靠手動指定或批量移動。「光輝」與「閃光」是兩個各自獨立的分類，系統不會替你推測歸屬。

`BUILTIN_RARITY_MAPPING_VERSION` **維持 5 不動**：`ensureSeeded()` 對資料庫裡不存在的分類會直接新增，不會碰既有分類；版本號一旦變動反而會把既有內建分類的對照整份重設，可能蓋掉使用者在設定頁改過的設定。

### 批量編輯（卡片分類頁，含待確認）

分類內容頁的篩選列下方有「☑ 批量編輯」。開啟後每張卡左上角出現勾選框（28×28，手機也好按），工具列提供：

- 已選取數量
- **全選目前頁面（N）** 與 **選取全部篩選結果（M）** 分成兩顆按鈕、各自標出數量，不會混淆
- 取消全選 / 結束批量編輯
- 「移動到分類…（N）」→ 確認視窗顯示卡片數與目標分類

切換分類、改搜尋或改篩選會清除選取並提示（改排序不會，因為卡片集合沒變）。

確認後整批寫在**同一個 IndexedDB 交易**裡，全成功或全不生效；成功後跳出帶「復原這次移動」的提示，逐張還原每張卡原本的手動分類狀態（原本沒有手動分類的會回到自動分類）。只改手動分類，收藏狀態、持有張數、卡片 ID、原始稀有度、備註與圖片都不動。

### 清除收藏（我的收藏頁）

「我的收藏」新增一整段「已收藏的卡片」清單，有搜尋、分類／語言／卡包篩選，以及同一套批量勾選。頁面上方有紅色的 **🧹 清除收藏…** 按鈕，點了會開範圍選擇視窗，不會立刻刪東西。

四種範圍：

| 範圍 | 說明 |
|---|---|
| 全部收藏 | 不受搜尋或篩選限制，連同**所有手動點亮紀錄**一起歸零 |
| 目前篩選結果 | 只清除符合目前搜尋／分類／語言／卡包的收藏，包含未顯示的部分 |
| 已勾選卡片 | 只清除勾選的；沒勾選時這個選項是停用的 |
| 指定條件 | 複選分類 + 可加選語言與卡包。同條件內複選取聯集，不同條件取交集 |

執行前的摘要會列出：清除範圍與條件、受影響的不同卡片數、即將清除的持有總張數、受影響的手動點亮紀錄數，以及「保留卡片、圖片、分類與備註」的提示。

**手動點亮紀錄的處理**：局部範圍預設只清實際卡片收藏；勾了「同時清除相關手動點亮」才會動它，而且只動能明確對應的。`species:<id>` 這種整隻寶可夢的點亮沒有語言／卡包資訊，一旦範圍縮到特定語言或卡包就**保留不動並在摘要說明筆數**，不會用猜的刪掉。

**防誤觸**：局部清除有確認與取消；「全部收藏」另外要求輸入「清除全部」四個字才會啟用執行按鈕。視窗裡另有「先下載 JSON 備份」按鈕。

清除只把 `count` 設為 0，**不刪除** `cardOwnership` 那筆紀錄（備註存在同一筆裡），更不會清空 IndexedDB 或刪資料庫。執行前會把受影響項目存成快照，之後可以「復原上一次清除」。復原時若某張卡在清除後又被重新收藏過，會先列出衝突筆數讓你決定要覆蓋還是只復原沒衝突的部分，不會直接蓋掉新操作。

## 已確認錯分修正（一次性）

使用者提供的 `PTCG_分類查核.xlsx`「錯分清單」中，**查核結果＝已確認錯分**的 31 張卡片，
由 [`step17_build_category_fixes.py`](data/pipeline/step17_build_category_fixes.py) 轉成
`data/category_fixes.json`。轉檔時已用語言、卡包代碼、完整卡號、卡名逐一核對過專案卡表，
31 張全數對上、0 筆失敗。「疑似錯分」27 筆與其他查核結果**一律不處理**。

修正內容：`SR → MA` 10 張（日版 M2a 超級進化）、`SR → SSR` 18 張（日版 SV4a）、
`UR → MUR` 2 張、`AR → CHR` 1 張。**逐張卡片 ID 指定**，不是把某個稀有度字串整批換掉 ——
所以不會把其他版本的 `Ultra Rare` 或 `Mega Hyper Rare` 一起改掉。

### 怎麼套用

收藏與手動分類都存在瀏覽器的 IndexedDB，開發環境讀不到，所以做成**設定頁的按鈕**：
「設定 → 套用已確認分類修正 → 檢視修正預覽…」。預覽會逐張列出四種狀態：

| 狀態 | 判定 | 處理 |
|---|---|---|
| 將套用 | 目前分類 == 清單的「目前所在分類」 | 改成建議分類 |
| 已經正確 | 目前分類 == 建議分類 | 跳過 |
| 衝突 | 兩者都不是（可能是你後來自己調過） | **保留原狀不動**，只列出來 |
| 找不到／版本對不上 | 卡片 ID 不存在或語言／卡包／卡號不符 | 跳過並說明原因 |

對話框內有「先下載 JSON 備份」。套用後會在提示裡提供「復原這次修正」。
批次版本記在 meta（`appliedCategoryFixVersions`），**不會在開機或重新整理時自動執行**，
所以套用之後你再手動調整，不會被改回去；重複執行也只會處理還沒套用的部分。

## 系列／卡包瀏覽與規則標記

底部導覽新增「📦 系列卡包」。

### 大系列

依**卡包所屬的系列**判定，不看卡片名稱 —— 卡名含「メガ／Mega／M」不代表屬於超級進化系列。
對照表在 [`js/seriesCatalog.js`](js/seriesCatalog.js) 的 `SERIES_CANON`，是掃過 `sets.json`
實際存在的 6 組（語言, seriesId）列出來的：

| 大系列 | 卡片數 | 卡包數 | 組成 |
|---|---:|---:|---|
| 劍＆盾 Sword & Shield | 5,471 | 40 | `en:swsh` + `ja:S` |
| 朱＆紫 Scarlet & Violet | 7,375 | 48 | `en:sv` + `ja:SV` |
| 超級進化 Mega Evolution | 3,000 | 18 | `en:me` + `ja:M` |

英文與日文的卡包**不會被合併**：各自保留自己的語言、卡包代碼與卡包 ID（`ja:M2a` 這種形式），
只是在瀏覽時歸在同一個大系列底下，進去後可以再用語言篩選。對不到 `SERIES_CANON` 的會落到
「系列待確認」，目前實際資料裡沒有這種卡包。

### 規則標記（Regulation Mark）

`cards.json` 當初沒保留這個欄位，而 step2 的原始 JSON 快取在專案搬家時已不在，
所以用 [`step16_fetch_regulation_marks.py`](data/pipeline/step16_fetch_regulation_marks.py)
重新向 TCGdex 要一次（**只抓 metadata，不重新下載任何卡圖**），輸出 `data/regulation_marks.json`。

三種狀態刻意分開，不混用：

| 顯示 | 意思 |
|---|---|
| `D`～`J` 等字母 | 來源明確給了 `regulationMark` |
| 無標記 | 來源有這張卡的資料，而且明確沒有這個欄位 |
| 待確認 | 這張卡還沒抓成功／來源回傳的值不合法 |

實際結果（15,846 張）：**有標記 15,100、無標記 728、待確認 18**。標記分布
A 3、B 1、C 1、D 1,360、E 1,914、F 2,034、G 3,151、H 2,831、I 2,897、J 908。
A／B／C 那 5 張都是日版促銷卡包（`SV-P`／`M-P`）裡的舊世代復刻（カプ・テテフGX、
デデンネGX 等），是來源真實資料，不是異常值。

待確認 18 張的來源：16 張是抓取失敗、2 張（`mfb-33 Potion`、`mfb-34 Switch`）
來源回傳了字串 `"None"`。`"None"` 不是合法的規則標記，雖然同卡包其他 32 張都確認
是「無標記」，但不能替來源斷定，所以一律留在「待確認」而不併入「無標記」。
另外 `mep-051` 來源回傳小寫 `"j"`，同卡包有 50 張是大寫 `"J"`，判定為大小寫誤植，
統一成大寫 —— 這是唯一做過的正規化，寫在 `sanitizeMarks()` 的註解裡。

標記**不是**用發售年份、卡包名稱、稀有度或卡名推算的，一律以來源欄位為準；
標記與系列世代是兩個不同欄位，也不等於現行賽制可用與否。

### 交叉篩選

`#/sets` → 選大系列 → 卡包，可同時套用：大系列、卡包、語言／地區、規則標記、
稀有度分類、已收藏／未收藏、關鍵字。切換大系列時，若原本選的卡包不屬於新系列會自動清除。

### 手動修正待確認欄位

卡片詳細頁每張卡下方有資訊區塊（大系列、卡包名稱與代碼、語言／地區、完整卡號、規則標記、
稀有度分類），按「修改系列／卡包／標記…」可手動指定，選好自動儲存、重新整理仍保留、
標示「手動指定」。卡包選單只列出該系列的卡包，避免系列與卡包對不上。

這些欄位存在獨立的 `cardFieldOverrides`（IndexedDB v4），**與稀有度分類、收藏、備註完全獨立** ——
改卡包或標記不會動到整理好的 AR／SAR／CHR 分類。之後更新來源資料時，手動指定一律優先。
JSON 備份已納入 `fieldOverrides`。

## 卡包排序（依發售日期）

預設 **由新到舊**，可在「系列／卡包」頁的排序選單切成「由舊到新」。選擇會記在
IndexedDB（`setSortDirection`），重新整理、換系列、換頁都沿用。

三個地方的卡包選單共用同一套排序：系列／卡包頁、卡片分類頁、我的收藏頁，
名稱前都會顯示 `YYYY/MM/DD`。

規則（實作在 [`js/seriesCatalog.js`](js/seriesCatalog.js) 的 `sortSets()`）：

- 用**該語言／發行地區自己的**卡包發售日期，日版與英文版各用各的
- 比較的是 `Date.parse()` 出來的時間值，不是直接比字串
- 同一天發售的，再依卡包代碼 → 卡包 ID 排，順序每次都一樣
- **缺日期或日期無效的一律排最後**（兩個方向都是），顯示「發售日期待確認」，
  不會被當成今天、匯入日期或 1970
- 先對「全部符合條件的卡包」排序，再分頁顯示

實測：劍＆盾 40 個卡包由 2023/01/20 排到 2019/11/15 嚴格遞減；同日發售的
Crown Zenith 與 Crown Zenith Galarian Gallery 相鄰且順序固定；切成由舊到新後
完全反向；偽造無日期與 `not-a-date` 的項目在兩個方向都沉底。

目前 106 個卡包**全部都有有效的 YYYY-MM-DD 發售日期**，沒有待確認的項目 ——
但機制已經做好，之後匯入缺日期的卡包會自動落到最後並標示。

## Android App 版

`android-app/` 底下是**收藏專用**的 Android 版本：可以瀏覽、搜尋、篩選、記錄收藏，
但**不能**修改卡片資料或分類。卡片分類、匯入匯出、資料整理一律留在電腦版。

完整說明見 [`android-app/README.md`](android-app/README.md)，這裡只講重點。

### 一份原始碼，兩種模式

App 版**不是**網頁版的複本 —— 兩邊共用 `js/` 底下同一份程式碼，差異全部由
`js/appMode.js` 的旗標控制，所以不會出現「改了網頁版忘了改 App 版」。

`android-app/build_www.py` 只做三件事：**複製、省略、換樁**，不改寫任何 JS 邏輯。

判定 App 模式有兩個獨立訊號，任一成立即可：`Capacitor.isNativePlatform()`，
或 `build_www.py` 注入 `www/index.html` 的 `<meta name="ptcg-app-mode">`。
**根目錄的 `index.html` 永遠不會有那個 meta tag**，所以網頁版一定是 `false`：

```bash
grep -c 'ptcg-app-mode' index.html      # 必須是 0
```

### 三層鎖定

一般使用者不能改分類或卡片主資料。這不是把按鈕藏起來，是三層各自獨立的阻擋：

1. **檔案不進 APK** —— `settings.js`、`exportPage.js`、`exporters.js`、
   `categoryFixes.js`、`rrRegroup.js`、`vendor/`、`sw.js` 都不複製；
   `categoryPicker.js` 與 `imageUpload.js` 換成保留 export 名稱的空實作。
2. **路由不註冊** —— `APP_ROUTES` 沒有 `/export`，`/settings` 指向一般設定。
   手動輸入 `#/export` 會得到「這個畫面在 App 版沒有提供」。
3. **資料層守衛** —— `js/db.js` 的 `tx()` 是全專案唯一開啟 IndexedDB 交易的地方，
   19 個寫入點都走它。守在那裡一次擋掉全部 11 個策展寫入函式，連以後新增的
   也自動涵蓋，而且從 console 直接呼叫模組 API 一樣擋得住。

被擋的 store：`categories`、`cardCategoryOverrides`、`cardFieldOverrides`、`customImages`。
照常可寫：`cardOwnership`、`manualFlags`、`meta`。

**誠實說明它擋不住什麼**：這不是沙箱。任何人在自己的裝置上用 DevTools 直接
`indexedDB.open("pokecard-dex")` 仍可繞過 —— 所有用 web 技術做的 App 都有這個限制。
資料是裝置本機、單一使用者、沒有後端，這個程度是相稱的。

### 手動分類怎麼進到 App

App 的 IndexedDB 與電腦版**不同源**（`https://localhost` vs `http://localhost:8811`），
資料過不去；而且守衛禁止寫入策展資料，也不能靠匯入塞進去。

所以改成**建置時烤成唯讀靜態檔**：電腦版「設定 → 匯出 JSON 備份」存成
`android-app/curation-source.json`，`build_www.py` 從裡面取出 `categoryOverrides`
與 `fieldOverrides`，寫成 `www/data/manual_overrides.json`。對 App 來說是唯讀的，
使用者改不了，但顯示的分類與電腦版一致。**守衛一行都不用鬆綁。**

> 在電腦版改了分類之後，APK 裡那份不會自己跟著變 —— 要重新匯出、重跑
> `build_www.py`、重新建置。

## 資料模型重點

- **「卡片原始稀有度」與「App 收藏分類」分開保存**：每張卡片的 `originalRarity` 欄位保留 TCGdex 資料庫原值（例如 `"Special illustration rare"`；這是 TCGdex 自己的英文正規化用語，不是卡面印刷文字，日文卡片也一樣回傳英文字串——這點在設定頁有說明）。分類（`categoryId`）是 App 載入時用「稀有度 -> 分類」對照表（存在 IndexedDB，預設值見 `js/categories.js`，可在設定頁調整）即時算出來的，調整對照表不會更動卡片本身保存的原始稀有度文字，也不需要重新匯入卡片資料庫。
- **V／VMAX／VSTAR／ex 等是標籤（`tags`）**：獨立欄位（來自 TCGdex 的 `stage`／`suffix`），可以和任何分類並存，不會跟稀有度混在同一個互斥欄位。
- **穩定 ID**：物種用全國圖鑑編號當 ID；卡片 ID 格式為 `tcgdex:{language}:{來源id}`（例如 `tcgdex:ja:SV2a-003`），`sourceId` 欄位保留 TCGdex 原始 id；分類用固定英文代碼（`NORMAL`／`AR`／`SAR`…）。收藏紀錄一律用這些 ID 關聯。
- **語言與版本分開保存**：同一隻寶可夢在日文版與英文版的卡片各自是獨立的卡片物件（獨立 id、獨立收藏紀錄），不會因為譯名相同就合併；同一卡包內卡號不同（例如一般版與 AR 版）也是獨立卡片。
- **四種分類狀態**：`owned`（已收藏）／`confirmed_not_owned`（已確認有，未收藏）／`confirmed_absent`（已確認沒有，機制保留但目前無資料填入，避免誤判）／`unknown`（尚未收錄或未確認）。首頁與詳細頁的分類徽章明確用不同樣式區分這四種狀態。
- **快速點亮 vs 精確收藏**分開儲存在不同的 IndexedDB object store（`manualFlags` 與 `cardOwnership`），互不覆蓋；取消快速點亮不會刪除精確收藏紀錄，若仍有實際持有卡片，畫面會維持點亮並顯示原因。

## 已完成的功能

- 全國圖鑑首頁：圖鑑編號、圖片、中文名、整體點亮狀態、分類徽章、已收藏卡片數、搜尋、篩選（世代／收藏狀態／分類／分類收藏狀態）、無限捲動載入（1025 隻寶可夢分批渲染，不會一次全部塞進 DOM）。
- 寶可夢詳細頁：整體狀態、各分類收藏狀態卡片（含「為什麼點亮」說明）、分類分頁切換、實際卡片清單（卡圖、系列、卡號、原始稀有度、分類、標籤、語言、發售日、繪師、張數 +/-、備註）。

- 缺卡清單頁：依分類／語言篩選，列出「已確認存在但尚未收藏」的卡片，分批載入（目前範圍內可能有上萬筆，做了分頁避免卡頓）。

## 如何新增／更新卡片資料

正式流程見 [`data/pipeline/README.md`](data/pipeline/README.md)：`step1_build_index.py` 列出目標系列的卡片索引 → `step2_fetch_details.py` 抓完整資料（有本機快取、失敗重試）→ `step3_aggregate.py` 整理成 `cards.json`／`sets.json` 並輸出匯入報告。要擴大匯入範圍（例如加入更早的系列），改 `step1` 的 `TARGET_SCOPE` 重跑即可，既有快取不會重抓。

若要手動修正單一卡片，直接編輯 `data/cards.json` 對應物件即可（欄位說明見 pipeline README），因為收藏紀錄是用 `id` 關聯，只要不改 `id`，既有收藏不會被打亂。

### 新增／修正寶可夢圖鑑資料
編輯 `data/species.json`。`id` 就是全國圖鑑編號，且是收藏資料關聯的 key，**不要重複使用或搬移既有 id**。

## 驗證過的情境

以下情境已在真實匯入的資料上手動測試通過（含全新裝置／全新瀏覽器 profile 與已有舊版收藏紀錄兩種情況）：

1. 收藏某張日文 SAR 卡（例如噴火龍 151 特別版）後，對應寶可夢與 SAR 分類徽章自動點亮，其他分類（AR／UR／PROMO…）不受影響。
2. 把最後一張已收藏的卡片張數歸零、且該分類沒有手動標記時，分類徽章正確恢復未點亮，並跳出可復原的提示。
3. 手動點亮某個分類（例如 SR）後重新整理頁面，狀態仍保留（IndexedDB 持久化）。
4. 分類狀態正確區分「已確認有、未收藏」與「尚未收錄／未確認」；稀有度資料缺失的卡片明確標示「稀有度資料尚未提供」，不會誤判成某個分類或「沒有推出」。
5. 匯出 JSON、原檔重新匯入（merge 模式）不會噴錯，收藏紀錄正確還原。
6. 收藏紀錄與圖鑑／卡片靜態資料分開儲存，卡片資料庫從第一版示範資料換成 TCGdex 正式資料後，既有收藏紀錄（含手動標記與實際持有卡片）自動遷移到新的卡片 id，未遺失；遷移只執行一次，且執行前會在 IndexedDB 留一份快照備份。
7. 分類對照表更新（本次新增了 Character Rare／Character Super Rare／Triple Rare 等稀有度字串的對應）後，既有使用者裝置上的內建分類會自動補上新對照，不需要清除資料重新開始。

同名但卡號／語言不同的卡片（例如日文版與英文版噴火龍）、以及一張卡對應多隻寶可夢，屬於資料結構本身的設計保證（各自獨立 `id`、`dexNumbers` 為陣列），且這次真實資料裡已有大量實例可互動測試（例如皮卡丘同時有日文與英文超過 100 種卡片版本）。
